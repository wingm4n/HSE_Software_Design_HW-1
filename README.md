## Структура и границы модулей

| Модуль | Ответственность |
|---|---|
| `Transports` | Иерархия транспорта: базовый `Transport` и наследники `Bicycle`, `EBike`, `Scooter` |
| `Things` | Вещи и устройства: `SafetyThing`, `DockStation` и др. |
| `Interfaces` | Роли: `IInventoriable`, `IEnergyConsumer`, `IBeginnerRated`, `IServiceCenter` |
| `Guard` | Проверка аргументов |
| `Application` | `FleetService`, `ServiceCenter`: учёт парка и техосмотр |
| `Console` (namespace `VyshKat.Cli`) | Меню, демо-сценарий, отчёты |
| `Program.cs` | Composition Root: регистрация зависимостей в DI |

Зависимости направлены внутрь: `Console` → `Application` → `Domain`. Namespace `VyshKat.Cli` выбран, чтобы не конфликтовать с `System.Console`.


## Решения, принятые в ходе проектирования:  
- в проекте разделяется бизнес-логика с абстракциями предметной области (Application + Domain) и консольный интерфейс (Console) -  это позволяет в будущем изменить UI на любой другой, не меняя бизнес-логику
- разделение Application и Domain позволяет добавлять новые типы объектов / новые бизнес-правила, не нарушая OCP
- явный CompositionRoot в Program.cs
- создан интерфейс IServiceCenter - позволяет мокать объект ServiceCenter для тестирования, правильно расширять решение на новые сервисные центры
- `FleetService` реализует основную бизнес-логику парка. При этом сознательно не создается интерфейс `IFleetService` - ведь в рамках решения такой объект является единственным и центральным, мокать его никто не должен 

## Соблюдение принципов SOLID + DI, обоснование
### DI
Dependency Injection явным образом реализуется в Composition Root (Program.cs) с применением соответствующего DI-контейнера (`ServiceCollection` из `Microsoft.Extensions.DependencyInjection`). Зависимостям назначаются разные жизнненые циклы в соответствии с требуемым поведением.

**Жизненные циклы в DI:**
- `FleetService` — Singleton, потому что хранит состояние всего парка, логически является единственным в рамках решения.
- `DemoScenario` — Transient, потому что демонстрация может вызываться многократно.

Так же DI используется в unit-тестах на поведение, в частности, при подмене техосмотра через mock.

### SOLID 
### Какой принцип применён наиболее явно и где

Наиболее явно применён **ISP**. Контракты разделены по ролям:

- `IInventoriable` — постановка на учёт (инвентарный номер);
- `IEnergyConsumer` — расход энергии, нужен техосмотру;
- `IBeginnerRated` — рейтинг простоты, нужен списку для новичков;
- `IServiceCenter` — решение о допуске по результатам техосмотра.

Например, `KneePad` не обязан иметь расход энергии, а `EBike` реализует `IBeginnerRated`, `IInventoriable`, `IEnergyConsumer`. `FleetService` использует только те интерфейсы, которые нужны операции.

Также явно выражен **SRP**: `FleetService` отвечает за учёт парка, `ServiceCenter` — за решение о техосмотре, `FleetReportPrinter` — за вывод отчётов, `ConsoleApp` — за ввод и меню, `Guard` — за проверку аргументов.

### Какой принцип ограничен и почему это приемлемо

Сознательно ограничен **LSP**. Метод `SafetyThing.Repair()` существует только у одной ветки иерархии `Things` и вызывается только в демо-сценарии. Он не часть общего контракта, поэтому код, работающий с базовым типом или интерфейсами, подстановкой подтипов не затрагивается. Метод оставлен как явная демонстрация полиморфизма в иерархии.


### Обоснование принципов SOLID

- **SRP.** Каждый класс имеет одну причину для изменения (см. выше).
- **OCP.** Новое правило техосмотра добавляется новой реализацией `IServiceCenter`, без правок `FleetService`. Новый вид транспорта добавляется наследником `Transport`. Ядро (`Domain`, `Application`) не меняется.
- **LSP.** Подтипы можно подставлять вместо базовых типов и интерфейсов, ограничение описано выше.
- **ISP.** Интерфейсы узкие и разделены по ролям (см. выше).
- **DIP.** Применён на границе `FleetService` → `IServiceCenter`: бизнес-логика зависит от абстракции техосмотра, а реализация подставляется в `Program.cs`. Консоль зависит от конкретного `FleetService`, так как отдельный интерфейс здесь не нужен.




### Расширение решения
При добавлении **нового вида транспорта** ничего не сломается - достаточно унаследовать его от `Transport` и добавить соответсвующую позицию в оболочку (Console).\
При добавлении **сотрудников** ничего не сломается - ведь интерфейс `IInventoriable` в хранилище `FleetService` позволяет ставить на учет только вещи (а не людей). Достаточно добавить абстракцию (интерфейс) сотрудника и хранилище для учета сотрудников, при этом не добавляя сотрудникам интерфейс `IInventoriable`. Тогда компилятор не позволит передать его в метод учёта.\
**Склад запчастей** - отдельная сущность с собственным хранилищем. `IInventoriable` реализуется, только если запчасти нужно ставить на инвентарный учёт. `FleetService` и существующие интерфейсы не меняются.


Другие варианты расширения программы (без трудоемкого переписывания кода в силу соблюдения **OCP**):
- добавление оболочек взаимодействия с `FleetService` - GUI, Web-интерфейс, файловый ввод и проч. Легко реализуется за счет разделения бизнес-логики (`FleetService`) и интерфейса взаимодействия (`Console`)
- добавление абстракций предметной области. Возможно в силу логической обособленности Domain и абстракций `Things` и `Transports`.
- добавление новых видов `ServiceCenter` и новых правил проведения техосмотра. Возможно в силу использования интерфейса `IServiceCenter`.

### Какой тест фиксирует правило техосмотра и правило для новичков, и как подменяется зависимость

**Техосмотр.** Решение о допуске принимает `IServiceCenter`. Реальная реализация `ServiceCenter` отклоняет транспорт с расходом энергии выше 3 кВт·ч. `FleetService` зависит только от интерфейса, поэтому в тестах его можно подменить.

- Тесты `FleetServiceTests`: `AddTransport_AddsVehicle_WhenInspectionApproves` (техосмотр пройден, транспорт попал в парк) и `AddTransport_RejectsVehicle_WhenInspectionDeclines` (техосмотр не пройден, транспорт в парк не попал).
- Подмена: в `FleetServiceTests` используется `Mock<IServiceCenter>`, который по настройке теста возвращает `true` или `false`.
- В консольных тестах `ConsoleHarness` подставляет `FakeServiceCenter`.
- `CompositionTests` проверяет, что регистрацию `IServiceCenter` в контейнере можно заменить, и `FleetService` получит подмену.

**Правило для новичков.** Транспорт попадает в список, если рейтинг простоты ≥ 6 (константа `FleetService.BeginnerSimplicityLimit`). Правило фиксирует тест `BeginnerFriendlyItems_Use_Threshold_Six`, который проверяет значения 5, 6, 7.



## Использование ИИ в работе
### Идеология
Ответственность программиста охватывает
- архитектуру, design
- глобальные решения по проектированию

- генерацию однотипного кода (например, в смежных классах иерархии)

- генерацию расширенных тестовых случаев, размножение тестовых случаев
- повышение процента покрытия тестами
- прочую монотонную работу с кодом - поддержание codestyle, naming, дополнительное комментирование
